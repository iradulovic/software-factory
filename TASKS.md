Last reviewed: 2026-09-22

## Agent workflow

1. Follow an explicit user-selected task when one is provided.
2. Otherwise, select the first unblocked item under **Next up** whose dependencies are complete. Preserve the listed order; dependencies are hard prerequisites, not permission to skip higher-priority eligible work.
3. Before editing code, move that entire item to **In progress**. Work on one tracker item per run.
4. Treat its acceptance criteria as the scope boundary. Record newly discovered work as a separate item instead of expanding the current task.
5. Apply the completion checks in `AGENTS.md`.
6. When every acceptance criterion is met, move the item to **Completed**, change `[ ]` to `[x]`, and add the completion date plus concise verification evidence.
7. If progress requires a user decision or unavailable dependency, move the item to **Blocked** and state the exact unblock condition.

Keep identifiers stable. Add new work at the appropriate priority position rather than renumbering existing items.

## Product direction and review baseline

This is a personal development assistant for one developer on one dedicated Windows desktop, using subscription-authenticated Codex and Claude Code within the user's two $20 plans. The target outcome is useful progress while the developer is away: locally validated changes, draft pull requests, GitHub CI evidence, and clear requests for human input. Human review, manual testing, and merging remain part of the workflow. Automatic deployment and online website inspection are not prerequisites.

Preserve the existing PostgreSQL state store, separate GitHub synchronization, isolated worktrees, explicit task transitions, shared process runner, independent validation, base-reference validation configuration, execution history, and human-controlled merging. Improve these boundaries incrementally; a rewrite or additional orchestration framework is outside this backlog's scope. Start with one coding execution at a time.

Optimize for accepted useful changes per week and manageable human review time. Lines changed, successful process exits, and total quota consumed are supporting signals, not success criteria. Preserve capacity for the developer's interactive sessions. Avoid automatic API-key fallback or paid overage; provider switching must respect each subscription's limits.

The 2026-09-22 review was primarily source inspection, not a live operational certification. It found gaps despite earlier completed tracker entries; the new tasks below supersede those entries' claims where relevant without rewriting history. During review, 37 core tests passed; the broader test invocation encountered missing OpenTelemetry references in the existing restore state, and fresh restore was blocked by access to the user-level NuGet configuration. This does not establish a source-code build regression. No live subscription-backed task or browser verification was performed.

Subscription facts are time-sensitive. Before implementing provider handling, verify installed CLI behavior and current official documentation. The review sources were [OpenAI usage documentation](https://learn.chatgpt.com/docs/pricing), [Claude Pro limits](https://support.claude.com/en/articles/8325606-what-is-the-pro-plan), and [Claude programmatic execution](https://code.claude.com/docs/en/headless). Usage varies by workload; five-hour and weekly constraints must not be reduced to a fixed task count or a guessed universal reset time.

- [x] **SF-614 — Surface GitHub CI status for the published commit** — Completed 2026-09-22. New `factory.task_ci_status` (migration 019, one row per task, upserted) holds the most recently synchronized CI status: `overall_status` (`Pending`/`Success`/`Failure`/`NoChecks`/`Unavailable`), the exact `head_commit`, each individual check, an `error` for a read failure, and `synced_at`. `IGitHubClient` gained `GetPullRequestChecksAsync`, deliberately separate from the existing `GetPullRequestStateAsync` (used only for merge/close resolution, left completely unchanged) since the two are fetched for different purposes and this keeps the well-tested merge-resolution contract untouched. It calls `gh pr view --json headRefOid,statusCheckRollup` — the head commit and every check fetched together, in the same call, so a check result can never be attributed to a different, possibly-stale commit than the one it actually ran against; this alone is what makes "stale successful checks on an older head never mark new changes green" true, since nothing is ever cached and compared across two separate fetches. `statusCheckRollup` mixes two shapes — a GitHub Actions check run (`status`/`conclusion`) and a legacy commit status (`state`) — both normalized into the same three-state `Pending`/`Success`/`Failure` per check (new `PullRequestCheck`), and a pure `PullRequestCiStatus.Overall` (`Factory.Core`, independently unit-tested, 5 cases) derives one overall status from the set: any `Failure` wins, else any `Pending` wins, else `Success`; zero checks is `NoChecks`, reported distinctly rather than folded into `Success` or `Unavailable`. "Missing checks/authentication errors remain explicit": unlike `GetPullRequestStateAsync` (which returns `null` on any read failure), `GetPullRequestChecksAsync` never returns `null` — a failure comes back as `PullRequestChecksResult(Succeeded: false, Error: <the actual gh stderr>)`, which `PullRequestCiStatus.Overall` maps to `Unavailable` and the sync worker persists verbatim, so the operator sees the real error text ("gh: authentication required," a network failure, etc.), never a generic "no status" that looks identical to "nothing configured." `Factory.GitHubSync.Worker`'s existing `ResolvePublishedTasksAsync` loop (unchanged for the merged/closed branches) now also syncs CI status for a `Published` task whose pull request is still open, upserting the row fully on every poll — never merged with the previous one, so a status can never survive next to a newer head commit; proven directly by an integration test that syncs three times (pending → success with more checks → a read failure) and asserts each call fully replaces the last, including a restart-safety check via a freshly constructed store. Local build/test validation (the existing `Build`/`Test` execution-timeline steps) and this CI status are kept visibly distinct — CI status has its own "CI status" panel on Task Details, never merged into the execution timeline or the change summary. Nothing here merges, deploys, or acts on a CI result automatically — this task is explicitly read-only surfacing; automatic CI repair remains out of scope, as stated. - [x] **SF-613 — Accept human feedback and continue existing task work** — Completed 2026-09-22. New `factory.task_feedback` (migration 018: task_id, body, created_at, created_by) is the durable, append-only record of every piece of operator feedback — nothing is ever overwritten or deleted by a later continuation, so "previous attempts remain auditable" holds for feedback exactly as it already did for `agent_run`/`task_event` history. New `ITaskStore.ContinueWithFeedbackAsync(taskId, feedback)` does two things atomically in one transaction: inserts the feedback row, then returns the task to `Pending` — from any resting state a human might reasonably act on (`Failed`, `WaitingForQuota`, `NeedsHuman`, `Rejected`, and, new transitions on `TaskStateMachine`, `ReadyForPublish` and `Published`), never mid-execution (refused, not thrown, from every executing status). "Define how an explicit human continuation grants a bounded new repair allowance after an earlier budget is exhausted": `ITaskStore.CountAgentRunsAsync` — the one query `WriteContextStep` already used to enforce `MaxImplementationAttempts` — now counts only `agent_run` rows since the task's most recent feedback timestamp (`COALESCE(max(created_at) FROM task_feedback, '-infinity')`), so a continuation always grants exactly one fresh `MaxImplementationAttempts`-sized allowance, never an unlimited one and never a permanently exhausted one; with no feedback ever recorded this is identical to the pre-SF-613 behavior (proven by a new integration test: two exhausted attempts, continue, budget reads back to zero, one new attempt counts only against the new cycle). A failure either way now raises a clearly labeled `InvalidOperationException` naming which case it was, rather than an unlabeled git error. Proven with real git commands (no mocks) in a new `GitRepositoryCacheTests` case: create a worktree, commit a change, remove the worktree exactly as `WorktreeCleanupExecutor` does (directory removed, branch left behind), then call `CreateAsync` again for the same task and assert the restored worktree's `HEAD` is still the earlier commit rather than a fresh one from base. - [x] **SF-611 — Add queue priorities and explicit task dependencies** — Completed 2026-09-22. New `factory.task.priority` (integer, default 0, higher first) and `factory.task_dependency` (migration 017: `task_id`/`depends_on_task_id` composite primary key, `CHECK (task_id <> depends_on_task_id)` against trivial self-loops, FK to `factory.task` on both sides). `ITaskStore` gained `SetPriorityAsync`, `AddDependencyAsync` (returns an `AddDependencyOutcome` — `Added`/`AlreadyExists`/`WouldCreateCycle`/`TaskNotFound`/`SelfDependency` — so the API can report the exact reason instead of a bare failure), `RemoveDependencyAsync`, `GetDependenciesAsync`, and `BlockDependentsOnFailedPrerequisitesAsync`. Cycle rejection: before inserting `task_id -> depends_on_task_id`, a `WITH RECURSIVE` query walks every dependency already reachable from `depends_on_task_id` and rejects the insert if `task_id` itself is among them — proven by a chained integration test (A←B←C, then A→C rejected as `WouldCreateCycle`) and idempotent re-adding of an existing edge (`AlreadyExists`, no duplicate row). "Claim ordering honors priority": `ClaimNextAsync`'s `ORDER BY` was already `priority DESC, created_at` from the original schema — verified (not re-implemented) with a new integration test proving a later-created, explicitly higher-priority task is claimed ahead of an earlier-created default-priority one. "Prove task B cannot run from a base missing task A": scoped deliberately to this repository's own reliable signal for "task A's change is actually available," not new git-ancestry verification machinery — `factory.task.status='Completed'` is already set only once `Factory.GitHubSync.Worker.ResolvePublishedTasksAsync` observes GitHub's own `merged: true` for that task's pull request, so a dependent's prerequisite really is merged and on the base branch by the time `status='Completed'`. `ClaimNextAsync`'s claim query gates a `Pending` row behind `NOT EXISTS (SELECT 1 FROM factory.task_dependency ... WHERE dep.status <> 'Completed')` — an unmerged prerequisite, at any status, makes the dependent unclaimable regardless of its own priority; a task already executing (recovering a stale lease) is unaffected, since it already started. Proven directly: a dependent task is never claimed while its prerequisite sits `Pending`, is claimed once the prerequisite's status is set to `Completed` (new integration test, `A_task_with_an_unmerged_prerequisite_is_never_claimed_until_the_prerequisite_merges`).
