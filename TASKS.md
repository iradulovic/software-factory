## Agent workflow

1. Follow an explicit user-selected task when one is provided.
2. Otherwise, select the first unblocked item under **Next up** whose dependencies are complete. Preserve the listed order; dependencies are hard prerequisites, not permission to skip higher-priority eligible work.
3. Before editing code, move that entire item to **In progress**. Work on one tracker item per run.
4. Treat its acceptance criteria as the scope boundary. Record newly discovered work as a separate item instead of expanding the current task.
5. Apply the completion checks in `AGENTS.md`.
6. When every acceptance criterion is met, move the item to **Completed**, change `[ ]` to `[x]`, and add the completion date plus concise verification evidence.
7. If progress requires a user decision or unavailable dependency, move the item to **Blocked** and state the exact unblock condition.

Keep identifiers stable. Add new work at the appropriate priority position rather than renumbering existing items.

## Product direction and review baseline

This is a personal development assistant for one developer on one dedicated Windows desktop, using subscription-authenticated Codex and Claude Code within the user's two $20 plans. The target outcome is useful progress while the developer is away: locally validated changes, draft pull requests, GitHub CI evidence, and clear requests for human input. Human review, manual testing, and merging remain part of the workflow. Automatic deployment and online website inspection are not prerequisites.

Preserve the existing PostgreSQL state store, separate GitHub synchronization, isolated worktrees, explicit task transitions, shared process runner, independent validation, base-reference validation configuration, execution history, and human-controlled merging. Improve these boundaries incrementally; a rewrite or additional orchestration framework is outside this backlog's scope. Start with one coding execution at a time.

Optimize for accepted useful changes per week and manageable human review time. Lines changed, successful process exits, and total quota consumed are supporting signals, not success criteria. Preserve capacity for the developer's interactive sessions. Avoid automatic API-key fallback or paid overage; provider switching must respect each subscription's limits.

The 2026-09-22 review was primarily source inspection, not a live operational certification. It found gaps despite earlier completed tracker entries; the new tasks below supersede those entries' claims where relevant without rewriting history. During review, 37 core tests passed; the broader test invocation encountered missing OpenTelemetry references in the existing restore state, and fresh restore was blocked by access to the user-level NuGet configuration. This does not establish a source-code build regression. No live subscription-backed task or browser verification was performed.

Subscription facts are time-sensitive. Before implementing provider handling, verify installed CLI behavior and current official documentation. The review sources were [OpenAI usage documentation](https://learn.chatgpt.com/docs/pricing), [Claude Pro limits](https://support.claude.com/en/articles/8325606-what-is-the-pro-plan), and [Claude programmatic execution](https://code.claude.com/docs/en/headless). Usage varies by workload; five-hour and weekly constraints must not be reduced to a fixed task count or a guessed universal reset time.

- [x] **SF-606 — Automatically perform bounded validation repair** — Completed 2026-09-22. Previous-attempt context (agent summary, failed build/test output, changed files) was already written into `.factory/task.md` on a repeat attempt (SF-202), but nothing ever automatically scheduled that repeat attempt — a failed validation always ended at `Failed` and sat there until a human clicked Retry. New `ValidationFailureClassifier` (pure, `Factory.Core`) classifies a failed build/test `ProcessResult` as `Repairable` (the default — most failures genuinely are code problems) or `Operational`: a narrow, deliberately conservative set of signatures (command-not-found text, POSIX exit code 127, authentication/401/403, DNS/network/TLS-certificate errors) that unambiguously indicate the environment itself is broken, where re-invoking the agent could never help. `ValidateStep` reports this via a new `PipelineStepResult.Repairable` flag (default `false`, so every other existing call site is unaffected without changes); `TaskExecutor` — the only place this is acted on, per the agent-boundary rule that orchestration decisions belong to the orchestrator alone — checks it against `context.Configuration!.MaxImplementationAttempts` using `context.AttemptNumber` (already known from `WriteContextStep`, no extra query): when a repairable failure still has budget left, the run closes as `Failed` (it genuinely did fail) but the task itself is transitioned straight back to `Pending` in the same step, attributed to `'orchestrator'` — functionally identical to a human's Retry, just immediate and automatic — so `Worker`'s very next poll cycle reclaims it into a fresh run that reuses the preserved worktree (unchanged: `GitWorktreeManager.CreateAsync` already reuses a recorded worktree) and receives the exact failed-command output through the existing previous-attempt context. Once exhausted, or for an `Operational` failure from the very first attempt, the task ends at `Failed` exactly as before, with an explicit reason naming the exhausted limit for the former. Budget accounting needed no new code to satisfy "restart cannot reset the budget" and "manual retry respects the same accounting": both the automatic reschedule and a human's `RetryAsync` return the task to `Pending`, and the next `WriteContextStep` counts the identical persisted `agent_run` rows via the unchanged `CountAgentRunsAsync` either way. Outcome and every acceptance criterion are met: a repairable failure with budget remaining is proven, end to end through the real `TaskExecutor` pipeline (fakes only at the process/store boundary, matching this project's established orchestrator-test convention), to close its run `Failed` and reschedule the task to `Pending` with an explicit "attempt N of M" reason (`TaskExecutorTests`, new); the same failure with no budget left is proven to end terminally with a reason explicitly naming the exhausted limit (new); an operational failure (a missing `custom-build` executable) is proven to never reschedule even though budget remains (new); `ValidationFailureClassifierTests` (new, `Factory.Core.Tests`) cover a plain compile/test failure as repairable, every operational signature (case-insensitively, in both stdout and stderr), and exit code 127 regardless of output text.
