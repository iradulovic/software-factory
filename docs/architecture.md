# Architecture

Agent profiles include a non-mutating authentication pre-flight command. The shared availability checker caches the short-lived result, and `AgentSelector` skips a failed provider with a structured profile/provider log so fallback and dashboard status use the same readiness signal.

Software Factory separates synchronized GitHub state (`github.*`) from execution state (`factory.*`). `Factory.GitHubSync` polls configured repositories through the authenticated `gh` CLI and creates tasks only for open issues carrying `factory:ready`. PostgreSQL prevents two active tasks for the same issue.

**Sync is incremental and convergent, not a full re-import every cycle.** `github.repository.last_synced_at` doubles as the sync checkpoint: `GhCliClient.GetIssuesAsync` searches `gh issue list` for issues updated at or after it (or every issue, the first time), sorted ascending, fully paginated in pages of 100 until a short page ends it — never the old single-call 100-issue cap. `Worker` only calls `IGitHubStore.MarkRepositorySyncedAsync` with the time the cycle *started*, not when it finished, so an issue that changes mid-cycle is safely re-fetched next time instead of silently missed, and a cycle that fails partway leaves the checkpoint untouched. Every comment is fetched per issue through `gh issue view` rather than trusted from `gh issue list`'s own nested (and capped) comments field, and `closed_at` is persisted alongside `state` on every upsert (label deletions and comment edits already converge for free, since labels are fully replaced and comments are upserted by id on every sync of an issue). An issue that is no longer open or no longer carries `factory:ready` has its `Pending` task — never one already active — cancelled by `ITaskStore.CancelPendingForIssueAsync` with an explicit reason recorded on `factory.task_event`; a reopened, still-eligible issue is simply picked up again like any other eligible issue next time it's fetched. `gh` CLI failures, including a detected rate limit, are still persisted per repository via `RecordRepositorySyncFailureAsync` regardless of which page or which issue they occurred on.

`Factory.Orchestrator` atomically claims one task with `FOR UPDATE SKIP LOCKED` and hands it to `TaskExecutor`, which runs an ordered pipeline of named steps: `PrepareRepositoryStep` (load repository/issue), `CreateWorktreeStep` (bare cache and isolated worktree), `WriteContextStep` (`.factory/task.md` plus the resolved validation configuration), `RunAgentStep` (select and invoke a configured CLI agent through `IProcessRunner` and interpret its result contract), `CollectDiffStep` (confirm the agent actually changed the worktree), `ValidateStep` (independent build/test commands), and `PreparePublicationStep` (an independently computed change summary — base/head commit, changed files, added/removed lines — plus a clean-worktree and expected-branch check). Each step returns an explicit outcome (succeeded, failed, needs human, waiting for quota) that `TaskExecutor` maps onto `TaskStateMachine`; a step never decides task status itself. A validated task rests at `ReadyForPublish`; the orchestrator never assigns `Completed` on its own — only `Factory.GitHubSync` observing a merged pull request does that. `TaskGitHubNotifier` posts a concise issue comment and sets one mutually exclusive `factory:*` state label (`factory:in-progress`, `factory:needs-human`, `factory:ready-for-review`, `factory:failed`) at each of those four outcomes, through the same `IGitHubPublisher` abstraction `PublicationExecutor` pushes and opens pull requests with; every write attempt, whether it succeeded or not, is recorded in the append-only `factory.github_write` table. `LeaseMonitor` renews the claim while a task executes. Every run, step, process result, and status transition is persisted, and every transition also appends a row to `factory.task_event` recording who caused it (`orchestrator` or `human`) and why.

**Every CLI coding provider is one `AgentProfile` and one runner/availability identity.** Codex uses a per-profile `Classes` mapping for quick and deep invocation settings; a task stores its provider and provider-neutral class separately. `AgentSelector` checks class support while applying provider-level pause, quota, and fallback policy. `CliAgentRunner` resolves model, effort, and arguments for the requested class at invocation time, including retry and independently configured review. New `agent_run` rows retain the class and actual model/effort; old preset-named rows remain intact. Migration 033 converts stored Codex-Luna/Sol task preferences to Codex plus quick/deep class without rewriting invocation history. The API aggregates all three historical/new Codex names for provider status, while details keep exact old run evidence.

**`QuotaClassifier` (pure, in `Factory.Core`) is the one place a quota signal is ever interpreted.** A successful invocation is never evidence of exhaustion, however its output reads — only a failed process's stderr is ever consulted, never stdout (which can legitimately narrate unrelated work that happens to mention a signature word) and never a successful exit. A matched signature is classified into a `QuotaWindow` (`ShortTerm` from `AgentProfile.QuotaSignatures`, or `Weekly` from the separately configured `WeeklyQuotaSignatures`, checked first) and a `QuotaResetKind`: `Reported` when the profile's optional `QuotaResetPattern` captures a `value` group that parses (an absolute timestamp or a relative duration), `Unknown` when that pattern matches but its captured value does not parse (still given a bounded backoff so the system does not wait forever, but never presented as a value the CLI actually reported), and `Estimated` otherwise, using the window's own configured cooldown hours as a bounded guess. `RunAgentStep` persists the result via `ITaskStore.RecordAgentQuotaStatusAsync` after every invocation, whether or not quota was detected, so a status that cleared is reflected immediately.

`WriteContextStep` also runs the repair loop: it counts how many times the agent has already been invoked for the task and, once that meets the repository's `maxImplementationAttempts`, fails the task there — before the agent runs again — with a reason explicit that no further automatic retry will happen. Below the limit, an attempt after the first has the previous attempt's agent summary, failed build/test output, and changed files written into `.factory/task.md`, so the agent fixes the actual problem instead of repeating its last approach. Quota exhaustion moves a task to `WaitingForQuota`, not aggressively retried, and `CliAgentRunner` records a reset via `QuotaClassifier` on the `factory.agent_run` row.

**A repairable validation failure schedules its own repair automatically, without a human clicking Retry (SF-606).** `ValidationFailureClassifier` (pure, `Factory.Core`) classifies a failed build/test `ProcessResult` as `Repairable` (a genuine code problem — the default, since most failures are) or `Operational` (the environment itself is broken: a narrow, deliberately conservative set of signatures — command-not-found, exit code 127, authentication/network/certificate errors — that re-invoking the agent could never fix). `ValidateStep` reports this on `PipelineStepResult.Repairable`; `TaskExecutor` is the only place that acts on it, exactly as the agent-boundary rule requires: when a failure is repairable and `context.AttemptNumber` (already known, set by `WriteContextStep`) is still below `maxImplementationAttempts`, the run closes as `Failed` (it genuinely did fail) but the task itself is transitioned straight back to `Pending` — the same effect as a human's Retry, just immediate and orchestrator-initiated (recorded with `actor='orchestrator'`, not `'human'`) — so `Worker`'s next poll cycle reclaims it into a fresh run that reuses the preserved worktree and receives the exact failed-command output via the existing previous-attempt context. Budget accounting is unchanged: the same `CountAgentRunsAsync`-backed count `WriteContextStep` already enforces, so a restart cannot reset it and a manual Retry after automatic repairs are exhausted hits the identical limit. Once attempts are exhausted, or the failure was `Operational` from the start, the task ends at `Failed` as before, with an explicit reason naming the exhausted limit.

**The `.factory/result.json` completion contract is generated, not hand-described (SF-605).** `TaskContextWriter` writes a full table of every field's type and requiredness, the exact accepted `status` values, and a JSON example into `.factory/task.md`'s `## Completion` section — both the writer and `AgentResultReader`'s actual validation read the same `AgentResultContract.Statuses` (`Factory.Core`), so the documented contract can never silently drift from what is actually accepted. The generated `## Constraints` section, and `CliAgentRunner`'s own prompt, both now explicitly require the agent to commit every intended change on its branch before finishing — previously nothing ever told the agent to, even though `CollectDiffStep` and `PreparePublicationStep` always required it. `CollectDiffStep` itself now rejects uncommitted changes immediately (`IWorktreeInspector.SummarizeAsync`'s `IsClean`), before a full build/test validation cycle is ever spent on work `PreparePublicationStep` would have rejected anyway at the very end; `PreparePublicationStep`'s own clean-worktree check is unchanged, a second, independent gate right before `ReadyForPublish`. `.factory/` itself was already excluded from every commit via the repository cache's `info/exclude` (SF-206), so an agent that runs a blanket `git add -A` still never commits its own generated context or result file.

**`Worker` resumes `WaitingForQuota` work from provider availability, never a waiting task's own invocation history (SF-604).** At the start of every poll cycle, before claiming, it calls `ITaskStore.ResumeExpiredQuotaTasksAsync` with the names of every currently configured `IAgentRunner` (resolved once via DI, `IEnumerable<IAgentRunner>`); the query resumes the single highest-priority `WaitingForQuota` task back to `Pending` only if at least one of those names is not currently at quota per `factory.agent_availability` — never by looking at that task's own last agent_run row, which fixes a task that was put into `WaitingForQuota` before ever being invoked (every configured provider was already at quota on its first attempt) and which previously had no reset record to resume from at all. It resumes at most one task per call, deliberately: bulk-flipping every waiting task to `Pending` the instant one provider frees up would let every task behind the first redo repository preparation and worktree setup for nothing the moment that provider's allowance runs out again (worker loops back to the next iteration immediately after finishing one, with no sleep, so genuine capacity still drains the queue promptly). Once a provider actually is available, mid-task provider fallback for the resumed task itself is `AgentSelector`'s existing, unchanged behavior — it already tries every configured agent, not only the task's preferred one.

**A quota-interrupted invocation never counts toward `maxImplementationAttempts` (SF-603).** `factory.agent_run.counts_as_implementation_attempt` (set by `RunAgentStep` to `!result.QuotaDetected`, migration 013) is a persisted classification separate from the append-only invocation history itself — every invocation is still recorded in full, in `factory.agent_run`, whether or not it counts toward the budget. `ITaskStore.CountAgentRunsAsync` and `GetPreviousAttemptAsync` both filter on this column, so the attempt count `WriteContextStep` enforces, and the "previous attempt" context it writes into `.factory/task.md`, always reflect real implementation attempts — never a quota blip, even one more recent than the last real attempt. Excluding quota interruptions from that budget cannot let a task wait on quota forever: `RunAgentStep` separately counts a task's accumulated quota interruptions (`ITaskStore.CountQuotaInterruptionsAsync`) against the repository's own `maxQuotaInterruptions`, and once that bound is reached, moves the task to `NeedsHuman` with an explicit reason instead of `WaitingForQuota` again.

A separate `PublicationWorker` polls `factory.publication` for requests — created by a human calling `POST /api/tasks/{id}/publish` on a `ReadyForPublish` task, or by the orchestrator itself when a repository's configuration sets `publish: auto-draft` — and hands each to `PublicationExecutor`, which pushes the task's own branch (refusing anything that isn't a `factory/…` branch or that matches the base branch) and opens a draft pull request through `gh`. A successful pull-request creation transitions the task to `Published`, a resting state distinct from `Completed`: nothing in the system ever merges a pull request, so completion isn't real until a human does. `Factory.GitHubSync` polls every task resting in `Published` and asks `gh` for its pull request's current state on each sync cycle, resolving it to `Completed` once merged or `Rejected` once closed without merge; an still-open pull request is left untouched. `Rejected`, like `Completed`, `Failed`, and `Cancelled`, is a terminal status that no longer blocks a fresh task from being created for the same issue, and it can be retried back to `Pending` like any other non-terminal failure.

**Publication recovers from a crash at any point instead of stranding a task (SF-607).** `ClaimNextPublicationAsync` claims the oldest `Requested` row exactly as before, but now also reclaims a `Publishing` row whose lease has expired (`FactoryOptions.PublicationLeaseSeconds`, default 300s, mirroring `factory.task`'s own lease pattern) — the worker that held it crashed somewhere between claiming and recording completion. Re-running a reclaimed attempt is always safe because every step `PublicationExecutor` performs is independently idempotent: it re-validates the worktree against `IWorktreeInspector.SummarizeAsync` (clean, expected branch, and — if `PreparePublicationStep` recorded one via the new `factory.task.validated_head_commit` column and `ITaskStore.SetValidatedHeadCommitAsync` — an exact match against the head commit that was actually validated, refusing to publish a worktree that has since moved on) before pushing again (a no-op if nothing changed since a prior successful push); and before calling `gh pr create` it first checks `IGitHubPublisher.FindExistingPullRequestAsync` for an already-open pull request on that branch, recording that one instead of creating a duplicate if a prior attempt's `gh pr create` had already succeeded on GitHub before the crash. The one interruption a reclaimed attempt cannot fix by re-running — a prior attempt recorded `PullRequestCreated` successfully but crashed before the task's own transition out of `ReadyForPublish` — is instead reconciled once per `PublicationWorker` poll cycle by `ITaskStore.ReconcilePublishedTasksAsync`, which finds any task still resting in `ReadyForPublish` whose latest publication already succeeded and completes that transition directly. Throughout, an authoritative resting-state change made by something else (a human cancelling the task while its publication is in flight) is never overridden: `PublicationExecutor` catches the resulting `InvalidOperationException` from `TransitionAsync` separately from every earlier failure path, leaving the task's own status alone while still keeping the pull request correctly recorded rather than reporting the publication as failed.

`Factory.Api` is a read/command boundary over PostgreSQL. `Factory.Web` is a polling Next.js client; it owns no workflow state. After SF-709, CI-green factory pull requests may auto-merge only when the captured repository policy allows it; requireHumanMerge defaults to true when omitted, and a HUMAN REVIEW issue marker always forces human merge.

**Large agent and validation output never goes to PostgreSQL whole.** Every `RunAgentStep`/`ValidateStep` invocation gives `IProcessRunner` a deterministic `LogsDirectory/{runId}/{stepId}.log` path (`StepLogPaths.Resolve`, computed once by `PostgresTaskStore.StartStepAsync` and persisted on `factory.step.log_path`); `ProcessRunner` streams stdout and stderr to that file, interleaved in arrival order, as the process runs, while only ever returning and persisting the last 64 KB as a bounded preview (`factory.step.output`/`factory.agent_run.stdout`/`stderr`). `GET /api/steps/{id}/log` serves the full file (404 if none was recorded, or if it isn't visible from wherever the API runs), and `?tail=true` returns just its last 64 KB — Task Details and Run Details poll that tail endpoint every few seconds while a step is `Running`, giving a live view of an agent at work.

**The dashboard shows real worker state, not an assumption that a worker is always running.** `Worker` calls `ITaskStore.RecordHeartbeatAsync` (an upsert into `factory.worker` keyed by `FactoryOptions.WorkerId`) at the top of every poll cycle when idle, the moment it starts executing a claimed task, and again on every successful lease renewal `LeaseMonitor` performs while that task runs — so the heartbeat stays fresh for the whole lifetime of a long execution, not just once per outer poll. `GET /api/workers` computes staleness itself (no `isStale` column) as `now() - last_seen_at` exceeding three times `max(PollingIntervalSeconds, LeaseHeartbeatSeconds)`, so it tolerates a couple of missed cycles without flapping. The dashboard sidebar shows the most recently seen worker's host and current task from this endpoint, and the four sidebar links to screens that don't exist yet (`/agents`, Pull requests, Logs, Settings) were removed rather than left as dead ends.

**A task's shown agent is whoever is actually invoking it, never just its preference, and the dashboard's agent status is resolved from real evidence, never hardcoded (SF-609).** `RunAgentStep` persists the selected agent's name onto `factory.task.current_agent` (`ITaskStore.SetCurrentAgentAsync`) the moment `AgentSelector` picks it — before the process starts, not only once it finishes — and clears it again in a `finally` block once that invocation ends, whichever way; `PostgresTaskStore.TransitionAsync` and the recovery branch of `ClaimNextAsync` also clear it defensively, so a crash mid-invocation can never leave a task looking permanently busy. Every place a task's `agent` is shown (`Factory.Api`'s `TaskListSql`, the issue-detail task list, and the `/api/tasks?agent=` filter, all built from one shared `TaskAgentExpr`) now resolves it as `current_agent` (an attempt actually in flight) → the most recent `factory.agent_run.agent` (the last attempt that actually ran) → `preferred_agent` (a task that hasn't run yet) → the configuration default — never just the preference alone, which a fallback away from it previously left silently misattributed. `AgentOperationalStateResolver` (pure, `Factory.Api`) is the one place an agent's displayed state is decided, combining the version-check outcome (never treating an unexpected exception from the check itself as a plain "unavailable" — that is `Unknown`, keeping one broken checker from ever failing the whole dashboard request), whether the operator has paused it (SF-610), `ITaskStore.IsAgentAtQuotaAsync`, `current_agent`-derived busy status, and whether the agent has ever completed a successful invocation, into `Unavailable`/`Unknown`/`Paused`/`QuotaBlocked`/`Busy`/`Verified`/`Installed`. The same resolution backs both `GET /api/dashboard`'s `agentStatus` and the new `GET /api/agents/status` the sidebar's header pill polls, through one shared `ComputeAgentStatusAsync`, so the compact pill and the full Overview table can never disagree. Quota reset information is now sourced from `ITaskStore.GetAgentQuotaStatusAsync` (the same independently persisted status SF-602 introduced) rather than re-derived from `agent_run` history, so the dashboard can finally show whether a reset time was actually `Reported` by the CLI, `Estimated` from a configured cooldown, or `Unknown` (a signature matched but its captured value didn't parse) — accurately, instead of presenting every reset the same way. `GET /api/dashboard` also now reports `metrics.needsOperator` (tasks resting in `NeedsHuman`) and a computed `idleReason` (no pending work, no available agent, or simply waiting to claim) whenever nothing is active, so "what needs the operator" and "why is nothing running" are answered directly instead of left for the operator to infer by cross-referencing tables.

Implementing this surfaced a real, independent, pre-existing bug: `AgentProfilesOptions.Profiles`'s own field initializer seeded the built-in default Codex profile directly on the property, and `ConfigurationBinder.Get<T>()` binds a configured `List<T>` section by *appending* to whatever the target list already contains rather than replacing it — so `appsettings.json`'s own `Agents:Profiles` (one Codex entry, coincidentally identical to the hardcoded default) was bound alongside that default instead of in place of it, registering every configured agent's `IAgentRunner` and `IAgentAvailabilityChecker` twice. `AgentProfilesOptions.Profiles` now defaults to an empty list; the "no configuration present" fallback moved to a separate `AgentProfilesOptions.DefaultProfiles` constant that nothing ever binds into, closing the gap structurally rather than by convention.

**Durable pause/resume reserves capacity for interactive use without touching work already in progress (SF-610).** `factory.dispatch_pause` (migration 016) holds one row per scope — `DispatchPauseScope.Global` for the whole factory, or a specific agent's own name — absence meaning not paused, so no seed data is required. `ITaskStore.SetDispatchPauseAsync`/`GetDispatchPauseAsync`/`GetAllDispatchPausesAsync`/`IsDispatchPausedAsync`/`IsAgentPausedAsync` are the only paths that read or write it; resuming (`paused=false`) clears the reason/actor/time along with the flag, so a later query never shows a stale reason for a pause no longer in effect. `Worker` checks `IsDispatchPausedAsync` once per poll iteration, immediately before `ClaimNextAsync` — never mid-task, so a task already claimed and executing always finishes undisturbed — while `AgentSelector.SelectAsync` checks `IsAgentPausedAsync` for each candidate alongside `IsAgentAtQuotaAsync`, skipping a paused agent in favor of the next configured one exactly like being at quota. `ResumeExpiredQuotaTasksAsync`'s own "is any configured agent available" check now also excludes a paused agent, so resuming a `WaitingForQuota` task never bypasses an operator's pause any more than it bypasses quota. `PublicationWorker` is deliberately untouched by either scope: pushing and opening a pull request for already-validated work consumes no agent's subscription capacity, so publication of a `ReadyForPublish` task proceeds regardless of pause — stated explicitly in the Overview panel, not left for the operator to guess. `Factory.Api` exposes this at `GET/POST /api/control/pause`, `POST /api/control/resume`, and `POST /api/agents/{agent}/pause`/`resume` (`PauseRequest.Reason` optional); the Overview page's "Dispatch running"/"Dispatch paused" panel and each agent row's Pause/Resume button call these directly, invalidating the dashboard, agent-status, and pause queries together on success so every panel reflects the new state at once, with an inline outcome banner (the same pattern `Task Details`' Retry/Cancel/Publish already use) confirming what happened.

**`WorktreeCleanupWorker` (a third, independently polling background service alongside `Worker` and `PublicationWorker`) removes worktrees for tasks that have come to rest, so they don't accumulate unbounded.** `WorktreeCleanupPolicy` (pure, in `Factory.Core`) is the single place that decides both halves of safety: which statuses cleanup ever considers at all (`Completed`, `Failed`, `Cancelled`, `Rejected`, `NeedsHuman` — every other status, including `WaitingForQuota`, is either still active or about to resume on its own and is never a candidate), and whether a given candidate path actually resolves inside the configured worktrees directory. `Failed` and `NeedsHuman` are retained by default (configurable via `WorktreeCleanup:RetainStatuses`) so a human still has something to inspect. For each eligible candidate, `WorktreeCleanupExecutor` clears the task's `worktree_path`/`branch_name` with a conditional update — `ITaskStore.ClearWorkspaceIfStatusUnchangedAsync`, which only succeeds if the status is still exactly what was last observed — *before* touching disk, deliberately in that order: if the task resumed in the meantime the clear simply fails and nothing is deleted, whereas clearing first means a worktree `CreateWorktreeStep` later needs will be freshly `git worktree add`-ed at the same deterministic path rather than expected to still exist. `IWorktreeManager.RemoveAsync` then runs `git worktree remove --force` (or, if the directory is already gone, `git worktree prune`) from the repository's cache — orchestrator-owned, like creation.

**Priority and explicit dependencies order and gate the claim queue, without new git-ancestry verification machinery (SF-611).** `factory.task.priority` (integer, default 0) and `factory.task_dependency` (migration 017: `task_id`/`depends_on_task_id` composite key, `CHECK (task_id <> depends_on_task_id)`, FK to `factory.task` both sides) are the only new state. `ITaskStore.SetPriorityAsync`/`AddDependencyAsync`/`RemoveDependencyAsync`/`GetDependenciesAsync`/`BlockDependentsOnFailedPrerequisitesAsync` are the only read/write paths. `AddDependencyAsync` rejects a self-dependency and a nonexistent task outright, then walks every dependency already reachable from the proposed prerequisite with a `WITH RECURSIVE` query and rejects the insert if the dependent itself is reachable — cycle detection done once, in application code, before the row is ever written, rather than as a database constraint that would need to re-derive the same graph on every write. `ClaimNextAsync`'s existing `ORDER BY priority DESC, created_at` already honored priority; SF-611 added the dependency gate alongside it: a `Pending` row is claimable only if `NOT EXISTS` a `factory.task_dependency` row whose prerequisite's `status <> 'Completed'` — an already-executing task recovering a stale lease is exempt, since it already started before any dependency could matter. "Task B cannot run from a base missing task A" is deliberately answered by this existing status signal rather than new `git merge-base --is-ancestor` verification: `factory.task.status` only ever becomes `Completed` once `Factory.GitHubSync.Worker.ResolvePublishedTasksAsync` observes GitHub's own `merged: true` for that task's pull request, so by the time a prerequisite reads `Completed` its change is already on the base branch — a narrower, explicitly scoped trade-off proportionate to this task's own "minimal dependency model" language, not a claim that literal commit-ancestry proof was implemented. If a prerequisite instead ends at `Rejected`, `Cancelled`, or `Failed`, its dependent must not stay queued behind a promise that will never resolve, and must not be silently released to run without it either — `TaskStateMachine` gained a `Pending -> NeedsHuman` transition, and `Worker`'s poll loop calls `BlockDependentsOnFailedPrerequisitesAsync` once per iteration (right after the existing quota-resume call) to move any such dependent to `NeedsHuman` with a `failure_reason` naming the specific blocking prerequisite and status — deliberately reusing `NeedsHuman` rather than adding a new status, so SF-609's existing `metrics.needsOperator` dashboard surfacing covers it with no further plumbing. A dependency edge carries no repository-equality constraint, so cross-repository prerequisites are allowed by construction, matching the scope's explicit support for independent issues across repositories while `ClaimNextAsync` still claims globally one row at a time. `Factory.Api` exposes `POST /api/tasks/{id}/priority`, `POST /api/tasks/{id}/dependencies` (409 with a specific reason on `WouldCreateCycle`/`SelfDependency`, 404 on `TaskNotFound`), and `DELETE /api/tasks/{id}/dependencies/{dependsOnId}`; `GET /api/tasks/{id}` additionally returns each dependency's prerequisite title and status (explicitly `.ToString()`'d, matching this codebase's established never-rely-on-`JsonStringEnumConverter` convention).

**Outstanding review work is bounded directly in the claim query, and freeing capacity reuses existing transitions rather than adding a new control (SF-612).** `FactoryOptions.MaxOutstandingReviewWork` (default 5; zero or negative disables it) caps how many tasks may rest at once in `FactoryTaskStatus.ReadyForPublish` or `FactoryTaskStatus.Published` combined — the operator's outstanding review backlog. The gate is one added condition on `ClaimNextAsync`'s existing `Pending` branch, in the same query the SF-611 dependency gate already lives in: `AND (@maxOutstandingReviewWork <= 0 OR (SELECT count(*) FROM factory.task WHERE status IN ('ReadyForPublish','Published')) < @maxOutstandingReviewWork)`. It applies only to a brand-new claim — the recovery branch (a task whose lease expired mid-execution) is unaffected, since that task already started before the limit could matter — and neither `PublicationWorker` nor `ITaskStore.ReconcilePublishedTasksAsync` reference it at all, so pushing/opening a pull request for already-validated work and completing a task whose pull request already merged both continue exactly as before; this is what keeps the limit from ever deadlocking the queue, and it is also how capacity frees itself — no new mutation was added, since a merge (via reconciliation) or an explicit cancel/reject already moves a task out of the two counted statuses. New `ITaskStore.CountOutstandingReviewWorkAsync` counts from `factory.task.status` directly, never from `factory.publication` rows, so a task with more than one publication attempt (the SF-607 stale-claim-reclaimed-and-superseded scenario) is never counted more than once. `GET /api/dashboard` exposes this as `metrics.reviewBacklog` and a `reviewBacklog: { count, limit, atLimit }` object, and extends the existing `idleReason` computation (SF-609) with a specific "review backlog limit reached" message, checked ahead of the "no agent available" fallback so the operator is never misdirected to check agent quota when their own review queue is the actual blocker; the Overview page shows a dedicated banner (matching the existing "Dispatch paused" panel's visual language) whenever `atLimit` is true, independent of whether other tasks are currently active, since in-progress work and publication both keep running while a new claim is paused.

**An explicit human continuation returns a resting task to implementation on its unchanged branch, grants a bounded fresh attempt budget, and restores a cleaned-up worktree's branch rather than orphaning it (SF-613).** New `factory.task_feedback` (migration 018) is a permanent, append-only record — nothing is ever overwritten, so every piece of feedback stays auditable even once a later one supersedes it. `ITaskStore.ContinueWithFeedbackAsync` inserts a feedback row and transitions the task to `FactoryTaskStatus.Pending` atomically in one transaction, from any resting status a human might reasonably act on (`Failed`, `WaitingForQuota`, `NeedsHuman`, `Rejected`, and two new `TaskStateMachine` edges, `ReadyForPublish -> Pending` and `Published -> Pending`) — never mid-execution. Reusing `Pending` means the very next `Worker` poll cycle reclaims the task through the entirely unmodified pipeline; the transition never touches `branch_name`/`worktree_path`, so a later publish reaches the exact same branch and `PublicationExecutor`'s existing `FindExistingPullRequestAsync` (SF-607) updates the same already-open pull request instead of opening a duplicate. `WriteContextStep` now also reads the task's most recent feedback (`ITaskStore.GetFeedbackAsync`) into `AttemptContext`, and `TaskContextWriter` renders it as a new `## Operator feedback` section in `.factory/task.md`, surfaced on every attempt within the current cycle (a repeat automatic repair from SF-606 still needs to see it, not just the attempt right after it was given). The implementation-attempt budget check `WriteContextStep` already enforced (`ITaskStore.CountAgentRunsAsync` against `RepositoryConfiguration.MaxImplementationAttempts`) now counts only `agent_run` rows since the task's most recent feedback timestamp — an explicit continuation always grants exactly one fresh, bounded allowance, never unlimited and never permanently exhausted; with no feedback ever recorded the count is unchanged from before SF-613 (the task's whole history). Separately, this surfaced a real, previously-latent gap in `GitWorktreeManager.CreateAsync`: `WorktreeCleanupExecutor` clears `worktree_path`/`branch_name` before removing a worktree but never deletes the branch itself from the shared cache, and the prior code unconditionally created a **new** branch from the base whenever those fields were unset — silently orphaning any already-pushed commits (and any already-open pull request) the moment a cleaned-up task was later retried or continued. `CreateAsync` now checks whether the deterministic branch name already exists in the cache (`git show-ref --verify --quiet`) before deciding: if it does, `git worktree add <path> <branch>` restores it with its commits intact; if not, the original from-base creation is unchanged. A failure either way raises a clearly labeled exception naming which case it was. Task Details gained an "Operator feedback" panel (history plus, for any continuable status, a feedback textarea and Continue button) backed by a new `POST /api/tasks/{id}/continue`, following the same inline-outcome-banner mutation pattern every other task action already uses.

**GitHub CI status is synchronized separately from `IGitHubClient.GetPullRequestStateAsync`, fetched together with the exact head commit it describes, and never silently swallows a read failure (SF-614).** New `factory.task_ci_status` (migration 019, one row per task, upserted) holds the most recently synchronized status: `overall_status`, `head_commit`, the individual checks as JSON, an `error`, and `synced_at`. `IGitHubClient.GetPullRequestChecksAsync` is deliberately a separate method from `GetPullRequestStateAsync` (used only for merge/close resolution and left entirely unchanged, preserving its existing tested null-on-failure contract) — it calls `gh pr view --json headRefOid,statusCheckRollup`, fetching the head commit and every check in the same call so a check can never be attributed to a different, possibly-stale commit than the one it actually ran against. `statusCheckRollup` mixes a GitHub Actions check run (`status`/`conclusion`) and a legacy commit status (`state`); both are normalized into the same three-state `Pending`/`Success`/`Failure` per check (`PullRequestCheck`). A pure `PullRequestCiStatus.Overall` (`Factory.Core`, independently unit-tested) derives one overall status: any `Failure` wins, else any `Pending`, else `Success`; zero checks is `NoChecks`, kept distinct from both `Success` and `Unavailable`. Unlike `GetPullRequestStateAsync`, `GetPullRequestChecksAsync` never returns `null` on a read failure — it returns `Succeeded: false` with the real `gh` error text, which `PullRequestCiStatus.Overall` maps to `Unavailable` and the sync worker persists verbatim, so an authentication or network failure is never presented identically to "no checks configured." `Factory.GitHubSync.Worker`'s existing `ResolvePublishedTasksAsync` loop (its merged/closed branches unchanged) now also syncs CI status for a still-open `Published` task's pull request, fully overwriting the row on every poll — never merged with a previous poll's result, so a stale status can never sit alongside a newer head commit. Task Details gained a "CI status" panel, kept visually and structurally separate from the execution timeline (local build/test validation) and the change summary — an overall badge, the short head commit, sync time, and each check with its own badge and diagnostics link.

**Outcome metrics are computed directly from existing history, windowed by when each thing actually happened, and deliberately report no lines-changed or remaining-quota figure (SF-617).** `OutcomeMetrics` (`Factory.Core`) is twelve fields, exactly what the task scope names: `ValidatedReadyForReview`, `MergedAccepted`, `Rejected` (kept distinct from `MergedAccepted` so rejected work is never silently folded into "accepted"), `Retries`, `QuotaWaitingEvents`, `HumanInterventions`, `AgentProcessSuccesses`/`Failures`, `CiSuccesses`/`Failures`, and an optional `AverageReviewMinutes`/`ReviewedTaskCount`. `ITaskStore.GetOutcomeMetricsAsync(since)` computes every count with one SQL query over `factory.task_event`, `factory.agent_run`, `factory.task_ci_status` (SF-614), and two new nullable `factory.task` columns (migration 020: `review_minutes`, `review_recorded_at`) — each windowed by its own event timestamp (`occurred_at`/`started_at`/`synced_at`/`review_recorded_at`), never by a task's `created_at`, so a long-lived task's older history never leaks into a later window. `Retries` counts a `task_event` re-entry into `Pending` from any non-null prior status *except* `WaitingForQuota`, which is counted separately under `QuotaWaitingEvents` instead — a quota resume is fallback recovery, not a retry of failed work, so conflating the two would misrepresent both. `AgentProcessSuccesses`/`Failures` (CLI exit code, excluding quota-interrupted invocations exactly as the existing `CountAgentRunsAsync` budget check already does) and `CiSuccesses`/`Failures` are kept as separate counters from `MergedAccepted`, and `ValidatedReadyForReview` stands in for "local validation success" — reaching `ReadyForPublish` already means the pipeline's own build/test validation passed, so no second counter says the same thing twice. `OutcomeMetrics`'s own doc comment states, and the model structurally enforces by omission, why no "remaining quota" or lines-changed field exists: no subscription CLI reports a real numeric remaining budget (only detected/reset-time, already tracked separately by SF-602's `AgentQuotaStatus`), and lines changed was never meant to stand in for productivity. Review time is optional and operator-entered only, via new `ITaskStore.SetReviewMinutesAsync` — never inferred — and a window with zero entries reports `AverageReviewMinutes` as absent, never as zero. `Factory.Api` exposes `GET /api/metrics?days=N` (default 7) and `POST /api/tasks/{id}/review-time`; the Overview page's "Outcomes" panel and Task Details' review-time control are both new, minimal additions following the codebase's existing panel and inline-outcome-banner mutation conventions.

**All three hosts export OpenTelemetry traces through one shared `Factory.Infrastructure.TelemetryExtensions.AddFactoryTelemetry`, configured entirely by the `Telemetry` section.** A single `ActivitySource` (`FactoryTelemetry.Source`, `Factory.Core`) is used by every host; which process emitted a span is the resource-level `service.name` attribute's job instead (`Telemetry:ServiceName`, defaulting per host to `Factory.Api`/`Factory.Orchestrator`/`Factory.GitHubSync`), not a separate source per host. With no `Telemetry:OtlpEndpoint` configured, no exporter is registered at all, so a missing or unreachable collector never affects startup. `TaskExecutor` tags one activity per run (task, run, and repository ids, plus the issue number when the task has one) and one child activity per pipeline step (task and run ids); `Factory.GitHubSync`'s `Worker` tags one activity per repository sync cycle (repository id), one when a task is created for an eligible issue (repository and issue ids), and one per resolved `Published` task (task id); `Factory.Api` tags a short activity on each single-resource endpoint (`/api/tasks/{id}`, `/api/runs/{id}`, `/api/repositories/{id}`, `/api/issues/{id}`, `/api/steps/{id}/log`, and the task retry/cancel/publish actions) with that resource's id. No span anywhere carries agent prompts, source content, process stdout/stderr, or secrets — only identifiers.

**A repository's own `TASKS.md` is a second, native task source alongside GitHub issues, with `Factory.GitHubSync.Worker` as the single component that both creates tasks from it and writes state back into it (SF-707).** `Factory.Core.TasksMdParser` is the one place the convention (`## In progress`/`## Next up`/`## Completed`/`## Blocked`, `- [ ]`/`- [x]` items, a nested `- Dependencies: SF-1, SF-2.` line — an intervening `### Priority N` sub-heading does not change an item's section) is read; every other heading (`## Optional backlog`, etc.) is `TrackerSection.Other` and never auto-eligible, matching `TASKS.md`'s own documented "promote only when requested" rule. `factory.task` gained `tracker_item_id` and `tracker_writeback_section` (migration 026) plus `task_type='TrackerFile'`, with `github_issue_id` left `NULL` — the same nullable-issue shape the publication path (`PublicationExecutor.DescribePullRequest`), `GitWorktreeManager.GetLocation`, and `TaskGitHubNotifier` ("a task with no linked GitHub issue is silently skipped") already handled before this task, so none of them needed to change. `ITaskStore.CreateForTrackerItemIfEligibleAsync` mirrors `CreateForIssueIfEligibleAsync` but is unique per `(repository_id, tracker_item_id)` *regardless of status*, never partial-by-status like `ux_factory_task_active_issue` — a tracker item is never recreated once it has ever produced a task, since the file itself, not GitHub, is the durable record of whether it is still open. `ReconcileTrackerDependenciesAsync` reuses the exact add/remove/cycle-skip logic `ReconcileIssueDependenciesAsync` (SF-710) already established (both now call a shared `ReconcileSourcedDependenciesAsync(taskId, source, parsed)`), tagged `source='tracker'` so it can never step on a `source='issue'` or manually-added edge; `factory.task_dependency`'s check constraint was widened to `source IS NULL OR source IN ('issue','tracker')`. Every cycle, `SyncTrackerFileAsync` reads `TASKS.md` from the repository's base branch (`ITrackerFileSync`, `null` if the file doesn't exist there — a repository with no tracker file is simply untouched), creates a task for each unchecked `Next up` item not already tracked, reconciles dependencies for every item, and writes back whichever `TrackerSection` (`TrackerSectionMapper.From`) each tracked task's live status now belongs in, if that differs from what the file was last confirmed to reflect (`tracker_writeback_section`) — the same role `TaskGitHubNotifier` plays for a GitHub issue's labels, except concentrated in this one already-polling component so a task claim (`Factory.Orchestrator`) and a completion (`Factory.GitHubSync`, once `ResolvePublishedTasksAsync` observes a merge) can never race each other into the same file. `TasksMdWriter.Apply` (pure, independently tested) relocates an item's *exact original lines* rather than reconstructing them, so hand-written `Dependencies:`/`Scope:`/`Acceptance:` bullets and prose survive a move untouched; it only ever toggles the checkbox (checked only for `Completed`) and, optionally, appends one new trailing nested bullet (verification evidence for `Completed`, the task's own `failure_reason` as the unblock condition for `Blocked`). `TrackerFileSync` (`Factory.Infrastructure`) writes without ever creating a worktree: `git read-tree`/`hash-object`/`update-index`/`write-tree`/`commit-tree` against a scratch `GIT_INDEX_FILE` inside the same bare `IRepositoryCache` cache `IWorktreeManager` already fetches, then a *plain* (never `--force`) `git push origin <sha>:refs/heads/<branch>` — git itself rejects a non-fast-forward the instant the base branch has moved since the read (a human's own commit, or a concurrent write), and a rejected push is simply left for the next poll cycle, which re-reads the file fresh and retries from there, so a human's own edit to `TASKS.md` is never overwritten or force-pushed over. Implementing this surfaced a real, independent, pre-existing encoding bug in `ProcessRunner`: a redirected process's stdin/stdout/stderr defaulted to .NET's OS-codepage encoding rather than UTF-8, silently mangling any non-ASCII byte (an em dash, in this task's own tracker file) written to or read from any git invocation — now always explicit UTF-8 on all three streams.

**A repository can opt into automatically serializing a batch of same-poll-cycle tracker tasks, instead of requiring each item to hand-author a `Dependencies:` line (SF-618).** Three tasks queued from the same `TASKS.md` sync pass with no `Dependencies:` between them are, by default, independently claimable — exactly the failure mode SF-619/620/621 hit: each started against a stale base branch, each independently re-discovered and re-patched the same pre-existing problem, and all three collided on `TASKS.md`/`.factory/config.json`/shared test-file edits across separate PRs. `RepositoryConfiguration.SerializeSameBatchTrackerTasks` (`.factory/config.json`'s `serializeSameBatchTrackerTasks`, default `false`) is the opt-in. `SyncTrackerFileAsync` already creates every eligible item's task in file order within a single pass; when the flag is set and more than one task was created in that pass, `SerializeSameBatchTrackerTasksIfConfiguredAsync` chains each to the one created immediately before it via a new `ITaskStore.AddTrackerBatchDependencyAsync`, tagged its own distinct `source='tracker-batch'` (the check constraint widened again, to `source IS NULL OR source IN ('issue','tracker','tracker-batch')`) so the edge is never read or removed by `ReconcileTrackerDependenciesAsync`'s own `source='tracker'` reconciliation of each item's hand-authored `Dependencies:` line, nor by a manual dashboard edit. The repository configuration is read once per sync pass, from the same bare `IRepositoryCache` cache `TrackerFileSync` already prepared moments earlier in the same call (`IRepositoryCache.GetPath`, no extra fetch), so a repository with the flag unset pays no additional cost at all.

## Durable boundaries

- `github.*`: repositories, issues, labels, comments.
- `factory.*`: tasks, runs, steps, agent invocations, publication attempts, worker heartbeats, an append-only `task_event` audit log of every status transition, and an append-only `github_write` log of every comment and label write attempted back onto GitHub.
- Repository cache: `{FactoryRoot}/repositories/{owner}/{repository}.git`.
- Worktrees: `{FactoryRoot}/worktrees/{owner}/{repository}/issue-{number}`.
- Step logs: `{LogsDirectory}/{runId}/{stepId}.log` — the durable path is recorded on `factory.step`, but the file itself is only ever written by the orchestrator and read by the API; they must share this directory (the same volume in Docker, or the same host) for log retrieval to work.

The orchestrator runs on the host so it can use local Git, SDK, GitHub CLI, and each configured CLI agent's authentication. PostgreSQL, API, and dashboard may run in Docker.
